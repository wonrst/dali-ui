적용을 중단한 이유

  1. HIGH는 품질을 만족했지만 비용이 컸습니다.
  2. PERFORMANCE는 filtering·메모리를 줄였지만 목표 FPS를 확보하지 못했습니다.
  3. ECONOMY는 더 저렴했지만 FPS 차이가 작고 한글 전환 품질이 더 떨어졌습니다.
  4. stage 제거 후보는 품질·정확성·GPU 비용 문제로 채택하지 못했습니다.

필요한 내용만 펼쳐보기

구현 구조 HIGH · PERFORMANCE · ECONOMY

앱이 줄마다 Label·BlurEffect·Animation을 따로 만들지 않아도 Reveal 시퀀스에 맞는 blur를 제공하는 것이 목표였습니다. 기존 progress·fade·stagger, 등장·퇴장과 reverse, 사용자 Animation 시간을 유지하면서 한글·gradient·ImageSpan 및 async 수명도 함께 검증했습니다.

Full은 W×H, X¼는 W/4×H, XY¼는 W/4×H/4입니다. W/H는 halo·packing을 포함한 Source 페이지 크기이며 축소 치수는 올림합니다. Output은 화면의 일반 renderer이므로 네 번째 offscreen 단계가 아닙니다.

HIGH — 품질 우선

Full Source → Full H → Full V → 화면

가장 안정적인 Gaussian 품질을 얻지만 filtering 면적과 intermediate texture가 큽니다. Source에는 이미 현재 Reveal progress가 적용되어 있습니다.

PERFORMANCE — 축별 quarter

Full Source → H (X¼, Y 유지) → V (XY¼) → V + 원본 Source

H의 Y를 보존해 조기 수직 축소의 artifact를 줄입니다. Late Smooth로 full Source에 복귀하며, 그 원본을 끝까지 보관하고 최종 합성에서도 읽어야 합니다. 같은 크기 H scratch는 공유할 수 있어도 페이지별 Source 유지 비용은 남습니다.

ECONOMY — H/V 모두 quarter

Full Source → H (XY¼) → V (XY¼) → 원본 × sharpAlpha + V × blurAlpha

추가 prefilter 없이 가장 작은 H/V를 사용합니다. 최종 설정은 authored radius와 gamma1/native timing이며, 이전 R32·gamma1.5 실험과 다릅니다. 일부 blur 격자는 덜 보이지만 한글 fade와 blur→sharp 전환은 더 부자연스러워 단순한 품질 순위로 볼 수 없습니다.

API 범위

연구 구현의 BlurRadius, BlurDurationRatio, BlurQuality 및 HIGH / PERFORMANCE / ECONOMY는 이번에 제품 contract로 출시하지 않습니다. 기존 blur 없는 Reveal은 이 결정과 별개입니다.

핵심 교훈 이번 연구에서 확인한 것
  1. Gaussian tap만 줄여서는 타겟의 큰 병목이 해결되지 않았습니다.
  2. page별 RenderTask/FBO/RenderPass와 의존성 처리가 중요하지만 task 개수 하나가 전체 원인은 아닙니다.
  3. PERFORMANCE/ECONOMY는 메모리를 줄여도 full Source와 3-stage 처리를 유지합니다.
  4. stage를 실제로 제거한 후보는 품질 또는 반복 계산 비용과 충돌했습니다.
  5. 앱이 끝난 효과를 None으로 해제하면 수명을 줄일 수 있지만 범용 플랫폼 최적화는 아닙니다.
  6. PC는 후보를 거르는 데 유용해도 타겟 FPS를 직접 예측하지 못합니다.
  7. batching·coverage·ownership 검증의 성과는 보존하되 다음 큰 개선은 렌더링 구조 수준의 과제입니다.
